# Workstation DNS ownership

Both `zen` and `t490` use the shared `desktop-services` NetworkManager service.
`dns=default` selects DNS from active connections, including DHCP-provided IPv4
and IPv6 servers and search domains. The declarative drop-in
`/etc/NetworkManager/conf.d/90-workstation-dns.conf` sets:

```ini
[main]
rc-manager=file
```

NetworkManager owns the writable `/etc/resolv.conf`. Do not install that file
through `etc-service-type`, add a placeholder, or hardcode public resolvers.
The [NetworkManager documentation](https://networkmanager.dev/docs/api/1.48/NetworkManager.conf.html)
describes `dns=default` and `rc-manager=file`; the latter writes resolver data
directly instead of delegating to resolvconf.

## Why Zen had connectivity but no DNS

The repository previously used `(service network-manager-service-type)` with
Guix's defaults. At our pinned Guix revision, `gnu/packages/gnome.scm` builds
NetworkManager with `-Dconfig_dns_rc_manager_default=resolvconf`. Openresolv
3.17.4's `lib/resolvconf/libc` refuses ordinary updates if the first line of an
existing resolver file is not `# Generated by resolvconf`. It reports a
signature mismatch. Thus DHCP can populate NetworkManager's internal DNS state
while libc applications keep reading a stale resolver file.

The working T490 has the expected openresolv header and its DHCP DNS server
`192.168.1.1`. Zen's reported `# Generated by placeholder` header fails the same
ownership check. Manual public nameserver entries restore lookups but do not
repair automatic DNS updates: they also fail openresolv's ownership check.

There is **no placeholder resolver declaration to remove from this repository**.
The older Guix 1.5.0 source present on the T490 creates a resolver placeholder
in `nscd-activation` (`gnu/services/base.scm`), inherited through `%base-services`,
when `/etc/resolv.conf` is absent. Its literal text is `# This is a placeholder.`,
not the exact header reported on Zen. The pinned Guix revision already removed
that creation code. This identifies a historical Guix placeholder mechanism,
but does not prove which installer/tool wrote Zen's exact reported text.
Reconfiguration does not automatically remove that pre-existing regular file.

The fix bypasses the ownership-header requirement. On DNS reload, NetworkManager
replaces the stale placeholder or temporary manual contents with current
connection DNS. It subsequently maintains the file as connections change.
No separate resolver daemon, global DNS addresses, DHCP/backend change, or
resolver-file deletion during activation is needed.

## Apply on each host

Keep Zen's working manual resolver until reconfiguration completes. On **Zen**:

```sh
cd ~/guix
git pull --ff-only
sudo ./scripts/guix system reconfigure -L modules hosts/zen/system.scm
sudo nmcli general reload conf,dns-rc
cat /etc/resolv.conf
nmcli -g IP4.DNS,IP6.DNS device show
getent ahostsv4 guix.gnu.org
```

On **T490**, use the same commands with `hosts/t490/system.scm`. The reload reads
the newly activated drop-in and republishes DNS without restarting NetworkManager
or intentionally disconnecting Wi-Fi. No reboot, new login or Home activation
is required. A future normal boot also loads this setting.

On the reported home network, expect `nameserver 192.168.1.1` from DHCP (plus any
other connection-provided DNS). On other networks the values should change.
No connection profiles were modified by this fix. Physical reconnect/reboot
behavior on Zen still needs verification after applying it.
